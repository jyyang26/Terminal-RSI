2 · GAE 设置与公式（本实现实际怎么算）

2.1 reward 如何注入序列

PPO 分支把整条轨迹的 shaped reward 作为一个 scalar 加在响应的最后一个 token 上， 其余位置的「reward」只有 KL 项（本配置 KL 系数为 0，故恒为 0）：

// slime/backends/megatron_utils/loss.py:739-750
elif args.advantage_estimator == "ppo":
    old_rewards = rewards
    rewards = []
    kl_coef = -args.kl_coef          # = -0.0
    cp_rank = mpu.get_context_parallel_rank()
    for reward, k in zip(old_rewards, kl):
        k *= kl_coef                 # 全零向量
        if cp_rank == 0:
            k[-1] += reward          # ← shaped reward 只加在最后一个 token
        rewards.append(k)
    advantages, returns = get_advantages_and_returns_batch(
        total_lengths, response_lengths, values, rewards, args.gamma, args.lambd)

所以 reward 向量是 r = [0, 0, …, 0, Rshaped]， 终局稀疏放置，信用由 GAE 沿序列反向回传。

2.2 GAE 递推（逐 response token）

实现在 slime/utils/ppo_utils.py。vanilla_gae（:482-503）是语义参考实现， 生产路径默认走数学等价的 chunked_gae（:506，128-token 分块加速）：

δ_t = r_t + γ · V_{t+1} − V_t (t = T−1 时 V_T ≡ 0，尾部零 bootstrap) A_t = δ_t + γ · λ · A_{t+1} returns_t = A_t + V_t ← critic 的回归目标
for t in reversed(range(T)):
    next_value = values[:, t + 1] if t < T - 1 else 0.0
    delta      = rewards[:, t] + gamma * next_value - values[:, t]
    lastgaelam = delta + gamma * lambd * lastgaelam
    adv_rev.append(lastgaelam)
full_returns = full_advantages + values

2.3 本配置（γ = λ = 1）下的闭式退化

把 γ = λ = 1 代入并做望远镜消去，所有中间 V 相消：

A_t = Σ_{l≥0} δ_{t+l} = (Σ_{l≥0} r_{t+l}) − V_t = G_t − V_t 其中 G_t = R_shaped（终局单点奖励，γ=1 不折扣） ⟹ 对整条轨迹的每个 token：A_t = R_shaped − V_t, returns_t = R_shaped
结论：当前 GAE = 纯蒙特卡洛优势
γ = λ = 1 时没有任何 bootstrap，优势的全部误差来自 baseline V 本身， 与序列长度无关（不存在「256k 上下文导致 return 爆炸」的问题）。 这也解释了为什么 §5 要把 critic 校准放在第一优先级： A = G − V 的符号由 critic 误差决定，而非任务成败。

2.4 CP=4 下的坐标处理

GAE 必须在完整序列上递推，但 context parallel 把序列切成 4 片。 get_advantages_and_returns_batch（:374）因此先 all_gather_with_cp 还原完整 values / rewards，在完整坐标上算 GAE，再 slice_log_prob_with_cp 切回各 rank。

两个已知的实现限制（不是 bug，但决定了 TB-GAE 的收益上限）
① get_advantages_and_returns_batch 不接收 loss_masks：GAE 递推会经过 observation（shell 输出）位置并读取这些位置的 V。value loss 本身已经用了 mask，但递推链与 loss mask 是两回事。
② 每个 sample 尾部是零 bootstrap，没有 episode 级的跨 Harbor-chunk 递推。 本运行 harbor_sample_mode = trajectory_retokenized，长轨迹会被切成多个 chunk （run #1 实测 1–5 个 / 轨迹，均值 3.04），因此跨 chunk 的信用传递是近似的。

3 · 是否使用了 TB-GAE？

未使用 本运行使用的是标准 GAE（γ = λ = 1，即纯 MC 优势）
证据：custom_advantage_function_path = None（若启用 TB-GAE 需通过该 hook 接入）； 参数转储中不存在任何 turn 级折扣参数 （γ_turn / λ_turn）；advantage_estimator = ppo 直接调用 get_advantages_and_returns_batch。
仓库里另有 slime_plugins/harbor/length_adaptive_gae.py（Length-Adaptive GAE）， 本运行也未启用——它仍按 response 位置递推，不跳过 observation，与 TB-GAE 不是同一个东西。

3.1 TB-GAE 是什么

Turn-Boundary Skip-Observation GAE，是针对「多轮工具调用 Agent」定制的优势估计器 （设计见 paper_list/tb_gae_vs_gae_comparison.html §4 与 reward_and_ppo_optimization_proposal_v2_measured.md 定制二）。它合并了两件事： 跳过 observation 节点（L5 Skip-Observation）与 turn/token 双时间尺度。

δ_t = r_t + Γ_t(1−d_t)·V(a_{t+1,0}) − V(a_{t,0}) A(a_{t,0}) = δ_t + Γ_t·Λ_t·(1−d_t)·A(a_{t+1,0}) Γ_t = 1（同一 turn 内） / γ_turn（跨 turn） Λ_t = 1（同一 turn 内） / λ_turn（跨 turn） d_t 只标记「真实环境终止」：训练切块与摘要边界处 d = 0 且传递 next-value， 保证终局 base reward 只在真实终止出现一次，不会被 chunk 复制计多次。 r_t 只落在第 t 个 turn 的最后一个有效生成 token。

3.2 TB-GAE 与标准 GAE 的差别

衰减在哪里发生 每个 response 位置乘一次 γλ（observation 位置也乘） turn 内 Γ=Λ=1（不衰减）；只在跨 turn 边界乘 γturnλturn

语义问题 要求 critic 预测「刚收到一屏 shell 输出之后」的状态价值 —— 一个模型从未被训练去预测的外部注入状态 V 只在「模型需要做决策」的状态上被监督，语义一致

折扣网格 文献惯例 {0.95, 0.99, 1} 必须用 {0.995, 0.999, 1.0}：本场景 42–57 turn，0.9550 = 0.077 会几乎抹掉早期决策的信用
过程奖励落点 只支持整条轨迹一个 scalar 加在末 token（当前接线） 天然支持 turn 级奖励：rt 挂在来源动作的末生成 token 上

关键的诚实结论：在 γ = λ = 1 下，两者的 return 在数学上等价
按 tb_gae_vs_gae_comparison.html §6 的等价性定理：在 γ=λ=1、单段完整轨迹、 turn 边界与 chunk 边界定义一致时， GtTB-GAE = GtGAE， 有效 action token 的 return 完全相同（run #1 实测 G = A + V 在 11/11 步误差 ≤ 0.001，浮点级）。

所以「换成 TB-GAE 就能提升 advantage 数值质量」在当前配置下是错误的说法。 TB-GAE 的预期收益只来自四项：① value 回归目标的语义一致性（只监督决策点）； ② observation token 移出回归目标 → 降噪；③ 为 turn 级过程奖励提供正确坐标； ④ 与上下文压缩天然组合、降低重复前向成本。
为什么本轮没有上 TB-GAE（优先级判断）
参考文档的明确建议是：「优势估计的细化」必须排在「critic 校准」之后。 run #1 实测 explained_variance 9/11 步为负、最低 −38.2， |V|/|G| 中位数跨度 276×，critic grad_norm 2192 对 clip_grad 1 —— 瓶颈在 奖励尺度 + critic 校准，不在优势估计器。
本轮（run #2）因此优先做了：CTRF 分母 20 → 82 + per-family（修奖励尺度）、 warm critic + 4 步预热（修 critic 起点）、critic value_clip 0.2 → 4.0 与 clip_grad 1.0 → 100（让 critic 真能更新）。 若这些做完 EV 仍为负，下一步才是 Skip-Observation → token-level TB-GAE， 且必须先做 γ=λ=1 下的等价性负对照（若不等价说明索引错位，先修 bug）。

4 · Reward 是怎么计算的

4.1 三层结构

Dense reward 不是数据集里预存的分数，而是每次 rollout 结束后在容器里现算的：

容器内：tests/test.sh ① judge.py → 逐场景、逐字段与私有 oracle 比较，输出 semantic_checks 判定通过与否只由退出码决定 → reward.txt ∈ {0, 1}（二值，未被改动） ② ctrf_from_judge.py --granularity semantic → 把 judge 已算出但原本丢弃的逐字段结果转成 CTRF： {"summary": {"tests": N, "passed": P, ...}} 只取 details[].semantic_checks，排除 7 个 hygiene check （workspace_nonempty / has_reconstruct_py / … ——光建文件不该拿分） 宿主机：harbor 把整个 verifier 目录拉回 trial 目录 slime 通过 sample.metadata["harbor_trial_uri"] 定位 <trial>/verifier/ctrf.json 训练侧：slime_plugins.harbor.partial_reward.test_count_progress_rewards

4.2 shaped reward 公式（本运行）

R_shaped = P / SCALE(family) 当 CTRF 有效（source = "ctrf"） R_shaped = r_terminal ∈ {0,1} 当 CTRF 缺失/损坏/为空（回退二值，不让已解出的任务得 0） R_shaped = max(R_shaped, 0.0) 只有下界，无上界 P = CTRF 里通过的语义检查项数 SCALE(family) = 该 family 的 p90（见 §8 全表）；表中没有的 family 回退全局 82.0

PPO 下不做 group normalization（_should_normalize 只对 grpo / gspo / reinforce++_baseline 返回真），因此 rollout/rewards 与 rollout/raw_reward 数值相同。

凸性函数本身：数学没问题，但破坏了「满分 = 1」的锚点

R(x) = x · (1 + λ·x/(1+x))， λ = 0.5 实算复核：R(0.5) = 0.5833 ✓（声称 0.58） R(1.0) = 1.2500 ✓（声称 1.25） R(1.5) = 1.9500 ✓（声称 1.95） 单调递增：是 二阶导 ∈ [0.016, 0.971] → 严格凸：是 R 达到 cap 2.0 的位置：x ≈ 1.54

三个数值都对，凸性与单调性也都成立。两点需要注意：

  • R(1) = 1.25 ≠ 1。「全部检查通过」不再等于 1.0，而是 1.25。这不是错误， 但它意味着 value_clip、EV、以及跟 harbor/reward_mean（恒 ∈[0,1]）的对照 都要按新锚点重新标定。若希望保留「满分 = 1」，把凸性项归一化即可： R = x(1+λx/(1+x)) / (1+λ/2)。
  • cap 2.0 在 x ≈ 1.54 就触顶，而 3 个 family 的满分 x 已达 1.55/5.12/8.27 （tree_sitter_grammar/cmake_build_config/openfoam_cfd）。 这些 family 的「刚好全对」与「超额完成」都是 2.0，梯度信息在最该区分的地方丢失。

修正方案：把难度与完成度拆成两个因子

提案的两个诉求（A 防刷分、B 给难题更多奖励）在单个标量分母里是矛盾的，但分成两个因子就相容：

完成度 c = min(P / total_f, 1) ← 用 family 自己的分母，恒 ∈ [0,1] 凸性 conv = c(1 + λ·c/(1+c)) / (1 + λ/2) ← 归一化，conv(1) = 1 难度权重 w_f = clip((p90_f / 82)^γ, 0.55, 1.45) ← γ = 0.25，不做信度收缩 R = conv(c) · w_f 上界 1.45，无需 cap

这样三条诉求同时成立：c 保证任何 family 的满分都在 1 附近（不会有 0.013 这种死区）； wf 让难 family 的满分拿到 1.45、易 family 只拿 0.55（提案想要的「更重要的检查项给更多奖励」）； conv 提供深水区的边际递增。以 cmake_build_config（total = 508）为例：

疑问 2：为什么橙点会低到 0.013？
openscad_parametric_cad 的检查项数就是 1（p90 = max = 平均 = 1）。 提案的收缩项 (n·p90 + m·82)/(n+m) 在 n=2、m=10 时把它拉到 68.5， 再经 82·(68.5/82)^0.5 压缩得到 Df = 74.9。 于是"唯一那 1 项全部做对"只拿 1/74.9 = 0.013。
这正是本节要指出的缺陷：它确实堵住了"1 个 check 拿满分"的刷分路径， 但代价是这个 family 的真正全部解出也变得与失败轨迹在梯度上无法区分。
疑问 3：为什么 3 个橙点都是 2.00？
因为撞上了提案自带的硬截断 R = min(…, 2.0)。 openfoam_cfd 的 x = 796/96.3 = 8.27，凸性后是 11.96，被截到 2.00； cmake_build_config x = 5.12，tree_sitter_grammar x = 1.55，都超过触顶阈值 x ≈ 1.54。 后果是这三个 family 的"刚好全对"和"超额完成"都是同一个 2.00，梯度信息在最该区分的地方丢失。

上线前必须补的两项验证（本文未做）
  1. 逐 trial 的均值与分位。上面所有数字都是「满分轨迹」口径，是上界， 不是实际训练里的均值。提案声称「均值保持 0.25–0.35」需要按 (family, passed) 逐 trial 重算 —— 这一步需要扫全部 trial 的 ctrf.json 并联合 result.json 的 task_name， 本文没有完成该统计，因此无法确认也无法否认该声称。

10.7 阶段 S2：基于 [p75, p90] 插值分母的生产级 CTRF 稠密奖励

10.4 定义的四支柱用的是全权重分母 （q_H = Σ_{c∈passed} W(c) / Σ_{c∈all} W(c)，即比例式）。 阶段 S2 改成 family 插值分母（绝对加权量除以该 family 的标定尺度）， 因为比例式把所有 family 的满分都拉平到 1.0，丢掉了「796 项检查的 openfoam 比 1 项检查的 openscad 难得多」这一信息；而纯 p90 绝对式（run #2 在用）又走到另一个极端。 S2 是这两者之间的可调折中，β 就是那个旋钮。

① 分母标定：[p75, p90] 凸组合 + 防刷分保底

S(f) = max( S_min , β·p75(f) + (1 − β)·p90(f) ) β = 0.50 p75 与 p90 的中点 S_min = 6.0 防作弊硬保底（检查项 1–5 的小 family 强制抬到 6） 缺失 family → 全局中点 (31 + 102)/2 = 66.5

β 的作用方向：β → 1 取 p75（典型样本尺度，大 family 分母变小、中间梯度变大， 但长尾难度被低估）；β → 0 退回纯 p90（run #2 的行为）。取 0.5 使 cmake_build_config 的分母从 506 降到 448、 openfoam_cfd 保持 796（其 p75 = p90 = 796，分布无长尾）， 让编译/调试的中间进度拿到可观测的正梯度。

② 成功优先与全局硬上界（Outcome Dominance）

B(τ) = Y + α·(1 − Y)·𝟙(Anti-Hack)·q_H(s_T), α = 0.50 Y ∈ {0,1} 环境独立终局硬判定（沙箱退出码 0 且全部隐藏用例通过 → reward.txt） q_H(s_T) = min( 1.0 , Σ_{c∈𝒫} W(c) / S(f) ) ∈ [0,1] R = clip(B(τ), 0, 1) ⟹ Y = 1（解出） → R ≡ 1.00 不论过程分多少 ⟹ Y = 0（未解出） → R ≤ α = 0.50 即便所有过程检查全过 ⟹ 刚性断层 = 1 − α = 0.50

α 由 0.30 上调至 0.50（iter19 生产运行）。动机是信号动态范围而非奖励幅度： run #2 的解出率使绝大部分批次样本落在 [0, 0.30]， 过程梯度被压在值域底部三分之一，而 critic 的 value head 必须张开到整个 [0, 1] —— 回归目标的有效方差远小于其输出范围。 α = 0.50 让过程分占据一半值域，未解出样本之间的区分度直接放大 1.67×。

关键不变量不受影响：刚性断层等于 1 − α， 只要 α < 1.0，「过程分拉满的未解出轨迹」就不可能追平、更不可能超过 「最弱的真实解出」。这不是一个靠调参维持的经验裕度，而是公式的结构性结论。 在 3326 条真实轨迹上复算确认（下表）：α 从 0.30 → 0.50 时未解出样本的上界精确地 从 0.3000 移动到 0.5000，解出样本恒为 1.0000，两侧零重叠。

为什么 2 步预热要写 7：该门控是绝对 rollout_id，不是「续训后的步数」
train_async.py:75： 
actor_trains_this_step = rollout_id >= args.num_critic_only_steps
从 iter_0000004 续训使 start_rollout_id = 5。 若直接写 --num-critic-only-steps 2，则第一步就有 5 ≥ 2 成立 —— actor 立刻参与，预热步数为 0，与意图相反。
要得到恰好 2 步 critic-only，必须写 start_rollout_id + 2 = 7： actor 在 rollout_id 5、6 冻结，在 7 解冻。启动脚本里按 $(( START_ROLLOUT_ID + 2 )) 计算而非硬编码，这样恢复点变化时仍然正确。

预热的必要性：奖励空间从无上界（实测 max 3.00）切到 [0,1]， 目标回报 G_t 的均值与方差同时变化。在 γ = λ = 1 的纯 MC 设定下 A_t = G_t − V_t，优势的符号完全由 V 的准确度决定； 而 iter_0000004 的 value head 是在旧尺度上训练的（run #2 实测 rollout/values 在 14–45 量级）。不预热直接更新 actor， 等于用一个系统性偏高的 baseline 算出的错误符号去推策略。

10.6 本方案没有解决的问题（必须明确）

  1. L2 首错 break 仍在。新奖励读的还是同一份 ctrf.json， 分母依然随候选存活深度漂移（45.7% 只暴露 1 个场景）。修这个要改 verifier 侧的 judge.py，属于独立工程。
  2. 数值容差穿透（abs_tol=1.0, rel_tol=0.25）未修。指令称 19.7% 的数值检查填 0 即过。 这一项我没有独立复核（需要对每个 leaf 检查重跑 oracle 比较）， 所以文中不把它当已证实的数字使用。反作弊闸门只能保证「至少命中一个 leaf」， 不能保证那个 leaf 不是被容差放过的 0。
  3. 判别力贫血（4.2% / 97.9%）未复核。该统计需要按 (task, check) 配对跨多次采样聚合， 扫描仍在进行，本文不引用这两个数字作为结论依据。 ι(c) 的熵权重设计不依赖它们成立 —— 它在任何 pass-rate 分布上都做正确的事， 但其收益大小要等该统计出来才能量化。
  4. 短程捷径坍缩假说未被证实也未被否证。当前删失掩盖了轮次信号， 必须先放开 max_turns、让分布散开，才能重新检验「模型是否偏好小任务」。
