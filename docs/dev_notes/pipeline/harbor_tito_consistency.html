0结论速览

通用文档把 TITO 失效归因为「decode → 结构化解析 → 模板渲染 → re-encode 往返」。 在本仓库里，这条往返不存在。真正的偏差来自另外两个机制，且性质完全不同。

安全
动作 token 从未被 decode-reencode。 llm.py:151 直接从 SGLang meta_info.output_token_logprobs 取 completion_token_ids，即模型实际采样出的 id；atif_adapter.py:864-865 把每一轮的 turn.output_ids 原样写进训练序列并置 loss_mask=1。见 §1。
安全
没有「结构化 tool_calls 再渲染回文本」这一步。 Terminus2 用 parser_name: json，assistant 的原始输出文本原样进 message history； llm.py:174 还额外存了一份 completion_text 用于文本级校验。见 §2。
需理解
Terminus2 会删改历史（摘要 / unwind / 截断长输出），但这不会把未 conditioning 的 token 混进 loss。 因为 adapter 的对齐是前缀锚定的：任何历史中段的删除都会让前缀匹配失败， transition 退化成 split，开一个全新的干净 chunk。代价不在正确性，在 credit assignment。见 §3。
需监控
存在一个有界的「边缘容差」窗口：prompt 尾部最多 96 token、response 两端各最多 16 token 的差异会被容忍并 stitch（记为 normalized_prefix）。这是唯一真正的小幅 TITO 偏差。见 §4.1。
已修复
rollout 128k context vs 训练 64k 尾部截断 —— 这曾是本 recipe 里最大的 TITO 破坏源， 2026-08-17 的改动已经把它修掉了：现在两侧同为 86016，agent 的 max_context_tokens 也从 128000 降到 86016（此前它高于 SGLang 实际服务的窗口）。 _hard_trim_plan 在正常情况下不再触发。仍需监控确认它真的是 0。见 §4.2。
真实问题
上面这些全都测不到。 adapter 已经算好了十几个 conditioning metadata key， 但 rollout.py 一个都没聚合上报；唯一能测量损伤的 train/tis_abs 诊断也是关着的。这一条至今仍然成立（已复查现脚本，无 GET_MISMATCH_METRICS）。见 §5。

1原始 token 全程回放：动作 token 没被重编码过

这正是通用文档第四节「底层核心：原始 Token 回放机制」要求的做法。本仓库已经是这样实现的。

1.1 采样阶段：抓的是 SGLang 真正吐出来的 id

# slime_plugins/harbor/llm.py:120-152（call() 内）
payload = {
    "input_ids": prompt_token_ids,      # 注意：送进去的是 token id，不是文本
    "sampling_params": sampling_params,
    "return_logprob": True,
}
...
meta_info = output.get("meta_info") or {}
token_logprobs   = meta_info.get("output_token_logprobs") or []
completion_token_ids = [int(item[1]) for item in token_logprobs]   # ← 实际采样的 id
logprobs             = [float(item[0]) for item in token_logprobs]  # ← 同一次前向的 logprob
两个关键点： ① 请求用的是 input_ids 而不是 text —— prompt 侧也不存在「服务端再 tokenize 一次」的二次分词； ② completion_token_ids 和 logprobs 来自同一个 output_token_logprobs 数组， 天然逐位对齐，不可能错位。

1.2 训练阶段：output_ids 原样进 loss

# slime_plugins/harbor/atif_adapter.py:864-867
# _normalized_trajectory_samples_from_detail 的主循环，每一轮都执行：
response_ids.extend(turn.output_ids)                 # 原始 completion_token_ids
loss_mask.extend([1] * len(turn.output_ids))       # 动作 token → 计梯度
rollout_log_probs.extend(_turn_log_probs([turn.output_log_probs], 0, len(turn.output_ids)))

turn.output_ids 就是 §1.1 抓到的 completion_token_ids，中间没有任何 decode / 模板渲染 / re-encode。三个数组（token、loss_mask、rollout_log_probs）在同一次循环里同步追加， 长度不可能对不上 —— 而且 atif_adapter.py:886-891 和 952-955 各有一道显式断言 （不一致就抛 RolloutConversionError）。

训练序列的组成部分loss_mask来源TITO 状态
首轮 prompt—（prompt 段） turns[0].prompt_ids 推理时 apply_chat_template 的产物，与推理完全同一份
每轮 assistant 输出1 completion_token_ids 精确 模型实际采样的 id
轮间 context（工具返回等）0 next_turn.prompt_ids[...] 取自下一轮真实送进 SGLang 的 prompt 的增量部分 —— 也是推理时用过的 id
注意第三行：轮间 context 并不是「把工具结果重新 tokenize 一遍」，而是从 next_turn.prompt_ids（下一轮真实发给 SGLang 的那串 id）里切出来的增量段。 所以即便这一段的分词边界与「单独 encode 工具输出」不同，它依然是推理时实际使用过的 id。 再加上它 loss_mask=0，不直接产生梯度。

3核心问题：Terminus 拼接会做删除，会怎样？

Terminus2 确实会删改历史 —— 摘要（enable_summarize: true）、上下文 unwind、 长工具输出截断，都会让「下一轮的 prompt」不再是「上一轮 prompt + 上一轮输出」的严格延长。 本仓库的代码注释自己就明说了这件事： 

# slime_plugins/harbor/atif_adapter.py:1261-1268（_stitch_turns_preserving_outputs 的 docstring）
"""Stitch Terminus-style prompts without dropping generated actions.

slime.agent.trajectory.merge_turns assumes later prompts are strict
continuations of the original chat token stream. Terminus2 re-renders each
decision point from the current terminal state, so a later prompt often has
a different base EVEN WITHOUT SUMMARIZATION. For Harbor training we keep
every assistant output as a supervised target and insert any intervening
prompt/context tokens as response-side tokens with loss mask 0."""
答案：删除不会污染 loss，因为对齐是「前缀锚定」的 —— 删除必然打破前缀，从而强制 split。 下面是完整的四条判定路径。

3.1 判定链：一次 transition 的四种归宿

对每一对相邻轮次 (turn[i], turn[i+1])，_normalized_transition_alignment （atif_adapter.py:996-1093）按顺序尝试：

① strict_prefix精确 TITO
atif_adapter.py:1004-1013

不成立 ↓
② normalized_prefix有界容差

三重搜索，允许有界的边缘差异：prompt 尾部丢 suffix_drop 个 （上限 = len(common_prompt_suffix) ≤ 96）， response 头尾各丢 leading_drop/trailing_drop （上限 max_response_edge_drop = 16）。 硬约束：_has_prefix(next.prompt_ids, prompt_base) 必须成立 —— 也就是上一轮 prompt（去掉≤96 尾 token）仍须是下一轮 prompt 的前缀。

为什么「删除」必然落到 ④：②③ 都要求 _has_prefix(next.prompt_ids, prompt_base)，而 prompt_base 只允许从 尾部裁掉 ≤96 个 token（_drop_suffix_len）。 如果 Terminus 删掉的是历史开头或中段的内容（摘要替换、unwind 旧轮次）， 那么无论怎么裁尾部，剩下的都不可能还是新 prompt 的前缀 ⇒ 所有候选 continue 掉， best is None ⇒ split。 删除在这套判定里是「无法伪装」的 —— 它不可能被误判成可拼接。
推断 关于摘要具体走哪条路：本机无 harbor 源码，无法直接读 terminus_2.py 确认摘要 是「整体替换 _messages」还是「保留 system 后替换其余」。但两种情况都落到 ④ split： 只要摘要改写了历史中段，前缀约束就破；就算摘要只保留 system 前缀， prompt_base（上一轮的完整长 prompt）也不可能是新短 prompt 的前缀。 另外摘要会让 completion_text != last_assistant_message_content，③ 也一并失效。

3.2 真正的代价：不是正确性，是 credit assignment 被切碎

split 保证了「不把未 conditioning 的 token 混进 loss」，但它确实改变了 RL 问题的结构。 一条轨迹被切成 N 个 chunk 后，每个 chunk 都是一个独立的 Sample： 

# slime/backends/megatron_utils/loss.py:743-750（PPO 分支）
for reward, k in zip(old_rewards, kl, strict=False):
    k *= kl_coef
    if cp_rank == 0:
        k[-1] += reward          # ← 每个 sample 的最后一个 token 加上完整 terminal reward
    rewards.append(k)
advantages, returns = get_advantages_and_returns_batch(...)   # ← 逐 sample 跑 GAE
后果机制严重性
terminal reward 被复制 N 次 loss.py:746 对每个 sample 都 k[-1] += reward N 个 chunk 各自当成一个「结局就是这个 reward」的独立 episode
GAE bootstrap 在 chunk 边界被截断 get_advantages_and_returns_batch 逐 sample 跨 chunk 的时序信用传播断了；早期轮次拿不到后期成功的折扣回传
梯度幅度不失控 group_mask_sums 按 group（=轨迹）归一 安全 每条轨迹的总 loss 权重保持不变
critic 的 value target 结构改变 每个 chunk 末尾 bootstrap=0 冷启动 critic 会低估长轨迹中段的 value
所以「怎么办」的答案是：不需要去修正确性（split 已经是对的）， 需要做的是知道 split 发生了多少次。 atif_adapter.py 已经把它记在 harbor_trajectory_normalized_split_after_turns 和 harbor_trajectory_num_chunks 里 —— 但这两个 key 从来没被上报到 wandb。 于是「我的 credit assignment 被切成了几段」这个问题，目前在训练时是不可见的。见 §5。

4残余风险：真正会造成偏差的两处

4.1 有界的边缘容差窗口（96 / 16）

路径 ② normalized_prefix 是唯一会容忍不一致并继续拼接的路径。它的窗口是有界的：

prompt 尾部 ≤ 96 token response 头部 ≤ 16 token response 尾部 ≤ 16 token

这个窗口的设计目的是吸收 Qwen 模板的 prefill 伪影（<|im_start|>assistant\n<think>\n\n</think>\n\n 之类，参见 examples/harbor_terminal_rl/harbor_normalized_trajectory_audit.py:11-24 的说明）。

一个容易误读的细节：leading_drop / trailing_drop 只作用于 output_projection（用来和下一轮 prompt 做匹配）， 不影响训练目标 —— atif_adapter.py:864 永远 extend(turn.output_ids) 全量。 所以 response_suffix_dropped_tokens > 0 的真实含义是： 「这一轮输出的尾部 k 个 token，在后续轮次的历史里被 Terminus 改掉/删掉了」。 我们仍然按原样训练这些动作 token（对动作本身是 TITO 精确的）， 但其后 token 的 conditioning 与推理时有 k 个 token 的偏差。 代码自己也知道这里可疑 —— atif_adapter.py:831-833 在 response_suffix_dropped_tokens > 0 时会给 routing replay 打 placeholder_first 标记。

相关 metadata（同样未上报）：harbor_trajectory_normalized_prefix_turns、 harbor_trajectory_normalized_prompt_suffix_dropped_tokens、 harbor_trajectory_normalized_response_{prefix,suffix}_dropped_tokens。

4.2 已修复：曾经的 128k rollout vs 64k 训练尾部截断

2026-08-17 的脚本改动已经修掉这一条。下面保留问题的机制说明（因为它是这类 bug 的典型样本， 也解释了为什么必须继续监控），但当前配置下正常情况不会触发。

曾经的矛盾

# 旧配置（已废弃）
yaml:  llm_kwargs.max_context_tokens: 128000   # agent 以为自己有 128k
sh:    SEQ_LENGTH = HARBOR_MAX_TRAIN_TOTAL_TOKENS = 65536   # 训练只有 64k

# slime_plugins/harbor/sample_postprocess.py:269-285 —— 截断策略是「保留尾部」
def _hard_trim_plan(total_length, response_length, cap):
    if total_length <= cap:
        return _TrimPlan(total_length, 0, response_length)   # ← 现在走的是这一支
    keep    = min(total_length, cap)
    dropped = total_length - keep
    prompt_length  = max(0, total_length - response_length)
    response_drop  = max(0, dropped - prompt_length)   # 先丢光 prompt，再丢 response 开头
# 调用处 sample_postprocess.py:149 —— sample.tokens = tokens[-keep:]  取尾部

当年的后果：超过 64k 的轨迹训练时只看到一个中段窗口，system prompt（任务说明、工具定义、 输出格式约定）和早期若干轮被丢掉，而 rollout_log_probs 是在完整 conditioning 下算的。 不报错、不 NaN，但 ratio 的分子分母来自两个不同的 conditioning， 且受害样本恰好是最长、最难、轮数最多的那批。

为什么现在不再触发

墙现值作用
训练 token 预算86016SEQ_LENGTH / HARBOR_MAX_TRAIN_TOTAL_TOKENS ⇒ _get_cap() 的 cap
agent 自认上限86016yaml max_context_tokens，由 llm.py:111-117 主动 guard
SGLang 服务窗口86016SGLANG_CONTEXT_LENGTH / SGLANG_MAX_PREFILL_TOKENS

关键在于 cap 与 agent 上限现在是同一个数（86016）。llm.py:111-117 保证 len(prompt) + max_new_tokens ≤ 86016，而 ROLLOUT_MAX_RESPONSE_LEN=8192， 所以任何一轮的 prompt + output 都 ≤ 86016 = cap。 再叠上压缩阈值 65536：一个 chunk 的跨度被压缩周期限制在 65536 + 8192 = 73728，比 cap 还低 12288。 _hard_trim_plan 因此走 total_length <= cap 的早退分支。

但仍然要监控，不能假设它是 0： ① 一个 chunk 可能跨越多个压缩周期（若某次 transition 走了 ②③ 而非 split， chunk 会继续累积）—— 理论上 stitch 的累积可以超过 73728； ② §4.1 的边缘容差每次 transition 最多引入 96+32 = 128 token 的对不齐， 59 次 transition 的理论上界是 7552 token（实际远低于此，因为压缩会强制 split）。
⇒ 盯 harbor/train_context_trimmed_sample_ratio，它应当恒为 0。 一旦非 0，说明有 chunk 累积超过了 84k，那才需要回来看这一节。
顺带一个新的观察点（压缩阈值 20000 → 65536）：压缩现在晚得多才触发。 由 §3 可知压缩边界会强制 split，所以： 压缩变少 ⇒ split 变少 ⇒ 每条轨迹的 chunk 数下降 ⇒ §3.2 的 credit-assignment 碎片化减轻（好事）； 但同时单个 chunk 变长、stitch 链更长 ⇒ §4.1 边缘容差的累积机会变多（需要看数据）。 这两个方向相反的效应，正好由 harbor/avg_chunks_per_trajectory + harbor/normalized_dropped_token_ratio 一起回答 —— 而这两个指标目前都没上报。

5怎么办：先让它可见，别急着改行为

§3 说明 split 机制本身是对的，不需要修；§4 的两处偏差都已经被算出来了， 只是没上报。所以第一优先级是可观测性，而不是改算法。

① 打开 mismatch 诊断（2 行 export，零算法风险）

export GET_MISMATCH_METRICS=1
export CUSTOM_TIS_FUNCTION_PATH=\
  slime_plugins.harbor.mismatch_metrics.record_only_tis_function

白拿 train/tis_abs —— 逐 token 直接测量 §4.1+§4.2 造成的 train/inference 分布漂移。健康值 ≈ 0.02。

已验证零代价：mismatch_metrics.py:82-84 原样返回 pg_loss/loss_masks； actor.py:491-505 表明 can_reuse_log_probs_in_loss 因 use_critic/keep_old_actor/use_routing_replay 早已为 False，compute_log_prob 本来就在跑 ⇒ 不增加前向。

5.2 明确不建议现在做的事

方案为什么先别做
切 harbor_sample_mode: turn 确实能拿到逐轮精确 TITO（_turn_samples_from_detail 完全不 stitch）， 但 ① prompt 在每轮重复 ⇒ 每条轨迹 token 量从 O(T) 变 O(T²/2)， max_turns=60 + MAX_TOKENS_PER_GPU 8192 下 step time 大概率不可接受； ② 每轮变独立 episode 拿满额 terminal reward ⇒ 与 parent 的轨迹级 GAE 是不同的 RL 问题。
新增 trajectory_strict（非 strict_prefix 一律 split） 会把 §3.2 的 chunk 碎片化放大，value target 结构变化更剧烈。 打破「算法与 parent 一致」。
丢弃被截断的样本 84k 对齐后 train_context_trimmed_sample_ratio 预期为 0 ⇒ 这个方案已无对象，不需要做。 （历史理由仍然成立：被截断的样本天然是最长最难的轨迹，丢掉会把 policy 往短/易任务偏， 并让 critic 见不到长上下文的 value regime。）
在转换处加 assert 抛异常 harbor_fail_on_conversion_error: true 会把 RolloutConversionError 变成整个 rollout 中止 （rollout.py:1204-1206）。一个模板空格差异就能干掉 88 张卡。 要做成只告警的软阈值。
