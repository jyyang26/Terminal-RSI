0三句话总览

① 谁在产生数据

Harbor 的 Terminus2 Agent 拿到一个终端任务（task.toml + instruction.md）， 在 Daytona 云沙箱里开一个真 shell，反复「想 → 敲命令 → 看输出」，最多 60 轮。 每一次「想」都是一次 HTTP 请求打到 SGLang 的 /generate。 跑完由 terminal-bench verifier 跑测试，得到 0/1 奖励。

② slime 在中间做什么

slime 是胶水与调度器：用 Ray 把 88 张卡切成「训练组」和「推理组」， 把 Agent 轨迹拼成带 loss_mask 的 token 序列， 按 group_id + 序列长度做 DP/micro-batch 装箱， 喂给 Megatron；训练完再把新权重 NCCL 广播回 SGLang。

③ 怎么学

标准 PPO：一个和 actor 同规模的 122B critic 与 actor 共用同一批 GPU（靠 offload 轮流上卡）， 用 GAE(γ=1, λ=1) 把最后一个 token 上的稀疏奖励摊成 per-token advantage， actor 用 ε=0.2 的 clipped policy loss。前 2 步只训 critic暖机。

为什么这套框架"看起来复杂"：普通 RLHF 的 rollout 是「一次前向出一段文本」； 这里的一次 rollout 是「启动一个云容器、跑一个可能长达 90 分钟的多轮 Agent 会话、再跑一遍单元测试」。 于是所有复杂度都集中在三件事上：(a) 长尾并发（280 并发试验、取最快 256、砍掉慢尾）、 (b) 把多轮对话无损切成可训练 token 段（trajectory_retokenized）、 (c) 单条 33k~64k token 的样本不可切分带来的显存与 JIT 编译风暴。

为什么 critic lr 要 30×：cold-start critic 的 value head 是随机初始化的（output_size=1， shape 不匹配时 model.py:_reinitialize_critic_output_layer 自动重init）。 一个没校准的 critic 会给出垃圾 advantage，所以要用极大的 lr 让 explained_variance 尽快从负值翻正，再叠加 NUM_CRITIC_ONLY_STEPS=2 的纯 critic 暖机。 YAML 注释里记录了历史：20× 时 EV 在 step30 首次转正（+0.11）。

2集群全景：88 张卡是怎么分的

Ray 先申请一个横跨 11 个节点、88 个 GPU bundle 的 placement group， 然后按偏移把前 64 个 bundle 划给训练、后 24 个划给推理。 critic 不占额外 GPU——它直接复用 actor 的 placement group。

为什么 TP 固定 2

GatedDeltaNet 用的是普通 nn.Linear（slime_plugins/models/qwen3_5.py，没有 Column/RowParallel）， 而 hf_attention.py 在调用它之前会把序列 all-gather 回全长。 所以 TP>2 时那 2.94B GDN 参数在每个 TP rank 上完全复制，激活峰值也不缩小。 加上 num_query_groups=2 < TP 会触发 KV 复制分支。⇒ 只能靠 PP 扛。

为什么调 EP 没用

专家参数占 116.0B / 121.4B（95.5%）。per-rank 专家参数按 1/(EP×ETP) 缩小， 但分布式优化器的分片因子 EDP = TP×CP×DP/(EP×ETP) 同比例变化，两者精确抵消： 专家优化器字节/卡 = P_expert × 12 / 训练总卡数。 ⇒ 只有加训练卡能降；降 EP 反而有害（权重+梯度翻倍而优化器不变）。

为什么 CP=2 值得 DP 减半

GDN 激活实测约 330 KiB/token，是真正会 OOM 的项。CP=2 把它砍半（10.57→5.34 GB @ T=33792）， 且 tests/test_qwen3_5_gdn_cp_*.py 验证前向逐位一致、梯度最大差 1.2e-7。 代价：DP 8→4，bs256 下每 rank 64 个梯度累积 micro-batch，step 时间约 4×。 脚本注释里写得很直白：correctness over speed。

3slime 在这里到底做了什么

slime 的定位是：把 Megatron（训练）和 SGLang（推理）用 Ray 缝在一起，中间夹一层 Data Buffer。 它自己不写模型、不写推理内核，只负责「资源编排 + 数据搬运 + 调度对齐 + 权重回灌」这四件事。 Harbor 这套终端 Agent 训练没有改 slime 核心一行，全部通过 --*-path 插件钩子挂进去。

slime 核心负责的四件事

① 资源编排 一个 placement group 覆盖全部 88 卡，按偏移切分 actor/rollout；critic 复用 actor 的 bundle； 每个 rollout 节点额外拉起一个 0-GPU 的 TrialWorker。slime/ray/placement_group.py
② 数据搬运 Sample 列表 → 训练用的扁平 dict（tokens / loss_masks / rewards / group_ids …） → 按 DP rank 切分 → ray.put() 成 4 个 Box。slime/ray/rollout.py:930-1100
③ 调度对齐 按 group_id 分组不打散、first-fit 装箱、micro-batch 数补齐到 DP 的倍数、 Karmarkar-Karp 均衡各 rank token 数——保证 PP 不失步。slime/utils/dp_schedule.py
④ 权重回灌 non-expert(TP) 与 expert(EP) 分两趟 all-gather、转 HF 命名、按 buffer 大小分桶、 NCCL 广播给引擎。update_weight_from_distributed.py

Data Buffer 到底是什么

slime 文档里说的"Data Buffer"不是一个消息队列，而是 DataSource 这一层抽象 + Ray object store。数据的物理落点只有两处： 

# ① 任务侧（prompt 侧）：HarborTaskDataSource 持有游标
  entries[]        # 14601 个 task.toml 条目，启动时扫描一次
  sample_offset    # 训练游标，取模循环 ⇒ 天然的 epoch 概念
  eval_* 游标      # 独立的 eval 池（89 个 TB2 任务），绝不与训练游标混用
  requeued_groups  # deque：被丢弃/失败的组可以回灌重试

# ② 训练侧（trajectory 侧）：Ray object store
  rollout_data_refs = [Box(ray.put(per_rank_dict)) for r in range(dp_size)]
  #  ↑ RolloutManager 在自己进程里 put 好，只把 4 个 ObjectRef 交给 driver
  #  ↑ 64 个训练 actor 里，只有各自 DP rank 对应的那一个会去 ray.get()
  #    ⇒ 大张量不经过 driver，也不走 NCCL；纯 Ray 共享内存
关键设计：轨迹数据用 Ray object store（CPU 共享内存）传，权重用 NCCL（GPU 直连）传。 前者数据量小（token id）但结构复杂、后者数据量巨大（122B × 2 bytes）但结构规整。分工非常清晰。

⑤ 轨迹 → Sample（本流程最微妙的一步）atif_adapter.py
_normalized_trajectory_samples_from_detail (L731-962)

难点：Agent 的第 k+1 轮 prompt 并不总是第 k 轮 (prompt+output) 的严格前缀扩展—— 摘要、history 截断、模板差异都会让它"漂移"。若强行当成一条连续序列，loss_mask 就会对错位置。 于是 trajectory_retokenized 模式逐对相邻轮次判定衔接策略：

策略含义处理
strict_prefix下一轮 prompt = 本轮 prompt+output + 新增尾巴尾巴作为「环境观测」拼进同一 chunk，loss_mask=0
normalized_prefix存在可容忍的前后缀漂移规范化后对齐，仍并入同一 chunk
retokenized_prefix助手文本重新 tokenize 后能对上用重 tokenize 的结果回放，保持 id 一致
split彻底对不上（例如刚做过摘要）切断，开一个新 chunk

结果：一条轨迹产出 1..N 个 Sample（chunk），每个 chunk 内： tokens = prompt_ids + response_ids， loss_mask[i] = 1 仅当该 token 是模型自己吐的， 环境回显的 stdout/stderr 一律 0。 同一轨迹的所有 chunk 共享一个 group_id： rollout_id×1e12 + group_index×1e8 + sample_rank×1e4 + detail_index。

group_id 为什么至关重要：它是 slime 唯一的「同一条轨迹」标识。DP 切分保证同组不跨 step； group_mask_sums 用整组的 mask 总数作 loss 分母， 于是即使 first-fit 把一个组的 chunk 拆到不同 micro-batch，各 micro-batch 的部分贡献相加后 仍然等于「每组一个 token 加权均值」。这是长轨迹训练里最容易算错的地方。

DP / micro-batch 调度的四步（slime/utils/dp_schedule.py:169-310）

1. 按组切 step

以 group_id 为单位切成每 global_batch_size=256 组一个 step， 同组样本永不跨 step。断言每 step 样本数 ≥ dp_size。

2. first-fit 装箱

first_fit_pack(lengths, max_per_bin = 8192 × CP)。 超大样本独占一个 bin，bin 和等于它自身长度——这正是 --max-tokens-per-gpu 拦不住 OOM 的原因。

3. 补齐到 DP 倍数

micro-batch 数必须是 dp_size × mb_group 的整数倍，否则 PP 会失步。 动态模式用 expand_bins_by_splitting（LPT）拆最大的多样本 bin 来凑数。

4. KK 均衡分配

balance_data 开启 ⇒ 用 Karmarkar-Karp 按 bin 的 token 总和分配给 4 个 rank （equal_size=True，各 rank micro-batch 数相同）。目标是压掉 straggler。

DP 越小，长尾越危险：KK 分区在 DP=1 时退化成单分区，无法把长样本"均衡掉"—— 这正是 88cp8-128k 预设（DP1）被标注为「慎用」的原因，也是 2026-08-11 那次 NCCL watchdog 击杀的 straggler 机制之一。

5一个训练 step 的完整时序

driver 侧的真实代码（train_async.py:63-105）

# 循环外：先把第一批 rollout 发出去

    rollout_data_curr_ref = ray.get(rollout_data_next_future)

        if actor_trains_this_step:
            ray.get(actor_model.async_train(rollout_id, rollout_data_curr_ref,
                                            external_data=value_refs))
        else:
            ray.get(value_refs)              # 前 2 步：只训 critic

    # ④ 周期性存档
    if should_run_periodic_action(rollout_id, save_interval, ...): ...

    # ⑤ 权重同步前必须先把在飞的 generate 收干净
    if (rollout_id + 1) % args.update_weights_interval == 0:
        rollout_data_curr_ref = ray.get(rollout_data_next_future) if ... else None
        rollout_data_next_future = None

    if should_run_periodic_action(rollout_id, eval_interval, ...):
        ray.get(rollout_manager.eval.remote(rollout_id))

读这段代码的三个要点

① 异步的收益与代价：rollout 约 20 分钟、训练也要几十分钟，重叠后 step 时间接近 max 而非 sum。 代价是训练用的数据来自上一版权重，即天然 off-policy——这正是 PPO 的 ratio 与 clip 要处理的对象。
② update_weights 前必须 drain：update_weights_interval=1（默认），所以每步都会 先 ray.get 掉在飞的 generate 再同步权重。否则权重会在生成中途被替换， 一条轨迹的前半段和后半段来自不同的模型，logprob 就没有意义了。
③ critic 先行不是随意排的：actor 计算 advantage 需要 values， 而 values 只能由 critic 前向给出。二者又共用 GPU，所以物理上只能串行： critic 上卡算 values + 训自己 → 下卡 → actor 上卡拿着 values 算 GAE + 训自己。

6训练方法：这一版 PPO 的每个决定

slime 支持 ppo / grpo / gspo / reinforce_plus_plus / reinforce_plus_plus_baseline。 这个 run 选 ppo——唯一需要独立 value 网络的那个，也是唯一会让显存翻倍的那个。

为什么在这个任务上选 PPO 而不是 GRPO

GRPO 的做法

同一 prompt 采 n 条，用组内 reward - mean（可选 /std）当 advantage， 不需要 critic。前提是 n 要足够大才有意义的组内基线。 

advantage_i = (r_i - mean(r)) / (std(r) + 1e-6)
这里的现实约束

一条轨迹 = 一个云容器 + 最长 90 分钟 + 一次完整单元测试。 n_samples_per_prompt=1 —— 采样成本让 GRPO 的组内基线根本无法建立（组里只有一个样本，减去均值恒为 0）。 所以必须用一个学出来的 value 函数当基线，即 PPO。

n=1 训练 / pass@3 评测

PPO 数学（slime/utils/ppo_utils.py + slime/backends/megatron_utils/loss.py）

Step 1 · 把稀疏奖励铺成 per-token reward（loss.py:738-750） 
kl_coef = -args.kl_coef                     # 本次 KL_COEF=0 ⇒ 整项为 0
for reward, k in zip(old_rewards, kl):
    k *= kl_coef                            # per-token KL 惩罚（此处全 0）
    if cp_rank == 0:
        k[-1] += reward                     # ★ 0/1 任务奖励只加在最后一个 token 上
    rewards.append(k)

也就是说：一条 3 万 token 的轨迹，reward 向量是 [0, 0, …, 0, 1] 或全 0。 把这个极端稀疏的信号分配到每个 token 上，就是 critic 存在的全部意义。

Step 2 · GAE 反向递推（ppo_utils.py:482-503 vanilla_gae，长序列走 chunked_gae 并行前缀扫描） 
δ_t   = r_t + γ · V(s_{t+1}) − V(s_t)
A_t   = δ_t + γλ · A_{t+1}                  # 从后往前
ret_t = A_t + V(s_t)                        # critic 的回归目标

本次 γ = 1.0, λ = 1.0（arguments.py 默认，脚本未改）。代入上式： A_t = Σ_{k≥t} δ_k = R − V(s_t)，其中 R 是轨迹终局奖励。 也就是退化成 Monte-Carlo advantage：不做时间折扣、不做偏差-方差权衡， 完全信任 critic 给出的状态价值作为基线。对"要么全过要么全不过"的终端任务， 中途并没有可信的即时奖励可折扣，这个选择是自洽的。

Step 3 · Actor: clipped policy loss（ppo_utils.py:125-149） 
ratio = exp(−ppo_kl)                # = π_new/π_old
L1 = −ratio · A
L2 = −clamp(ratio, 1−ε, 1+ε_high) · A
L  = max(L1, L2)                    # 悲观取大
clipfrac = (L2 > L1)                # 监控指标
  • EPS_CLIP=0.2，未设 eps_clip_high ⇒ 对称 [0.8, 1.2]。
  • KL 项关（USE_KL_LOSS=0）⇒ 不加载 reference model，省一整份 122B 显存。约束完全靠 clip。
  • 熵项关（ENTROPY_COEF=0）但仍以 no_grad 记录熵——熵崩塌是策略退化的首要征兆。
  • KEEP_OLD_ACTOR=1 ⇒ ratio 的分母来自训练侧的 old_actor 快照， 不是 rollout 引擎返回的 logprob（USE_ROLLOUT_LOGPROBS=0）。
Step 4 · Critic: clipped value loss（loss.py:1146-1201） 
v_clip = v_old + clamp(v − v_old, −c, +c)   # c = value_clip = 0.2
L = max((v_clip − ret)², (v − ret)²)
  • 诊断指标 explained_variance = 1 − Var(ret − v)/Var(ret)（loss.py:574-668，跨 DP+CP 全局归约）。 这是判断这个 run 健康度的第一指标：EV 由负转正说明 value head 开始真的学到东西。
  • value head 是 output_size=1 的新层，冷启动随机初始化，所以 lr 给到 30×。

为什么 USE_ROLLOUT_LOGPROBS=0（一个容易被忽略但很关键的选择）

Harbor 的 LLM 后端无条件把 SGLang 返回的 output_token_logprobs 写进 sample.rollout_log_probs， 所以这些数据一定会流到训练侧。但 USE_ROLLOUT_LOGPROBS=0 意味着不用它们当 PPO ratio 的分母， 而是让 actor 在训练前重新前向一遍算出 old_log_probs。

用 rollout logprob 的问题：SGLang 与 Megatron 是两套完全不同的实现 （kernel、精度、并行方式都不同，SGLang 甚至自带一份 fla 副本）。二者的 logprob 存在系统性偏差， 直接当分母会给 ratio 引入与策略更新无关的噪声。
代价与补偿：多一遍 122B 前向。但换来 ratio 在数值上严格自洽。 偏差本身仍可观测：打开 GET_MISMATCH_METRICS=1 + record-only TIS 函数， 可以在不改动 loss 的前提下把 train/tis、train_rollout_logprob_abs_diff 记进 W&B。
这也解释了脚本里 FLA_INTRACARD_CP=0 的必要性：fla 0.4.2 在 inference_mode 下对 ≥24576 token 的序列 自动切换另一套前向算法，数值会变。若不关掉，训练侧 logprob 与 rollout 侧就会失配。

通道 A · 权重（GPU→GPU）

NCCL 广播。训练侧 rank 0 + 全部引擎 GPU 组成一个专用进程组 slime-pp_{pp_rank}。数据量最大，每步一次。

Agent（跑在 rollout 节点的 TrialWorker 里）→ SGLang router → 某个引擎。 POST /generate，纯 JSON，走 token id。

通道 C · 轨迹数据（CPU 共享内存）

Ray object store。RolloutManager put，训练 actor 按 DP rank get。 不经 driver、不走 NCCL。

  • 为什么 --max-tokens-per-gpu 救不了：first_fit_pack 的文档明确写着 「超大样本独占一个 bin，bin 和等于它自身长度」。样本不可切分， 一个 40k token 的样本无论 cap 设多小都会自己占一个 micro-batch。 这就是把 8192 降到 4096 没用（只是让 micro-batch 数翻倍、更慢）的原因。
  • 真正的解：(a) 加训练卡降专家优化器项（唯一有效的杠杆）；(b) 提 PP 降 layers/stage， 对所有样本包括超大样本都生效；(c) CP=2 把 GDN 激活砍半。
失败 2 · Triton 冷编译风暴导致 NCCL watchdog 击杀CP>1 专属
2026-08-11，既不是死锁也不是 OOM。critic 的 per-microbatch 耗时呈 489s → 216s → 128s → 88s → ~22s 的典型 JIT 预热曲线。
  • 机制：变长终端轨迹（min ~800、max 35855 token）+ 动态装箱 + pad_size = TP×128 = 256 ⇒ 每步约 60 种不同的 padded thd 形状，每种新形状触发一次 GDN/Triton 编译（数十至数百秒）。CP=2 让 per-rank 长度减半，形状种类又翻倍。
  • 为什么日志是「15 个超时 + 1 个静默 rank」：rank 30 卡在 >30 分钟的编译里， 它的 15 个 EP 同伴早已进入 MoE all-to-all 并触发 30 分钟 watchdog； rank 30 因为压根没走到那个 collective，自己反而没超时。
  • 三件套修复：DATA_PAD_SIZE_MULTIPLIER=2048（把 60 种形状收敛成几种）+ TRITON_CACHE_DIR 指向节点本地 /root（跨 step / 跨 actor-critic 切换 / 跨进程重启都命中，且不像共享 fs 那样跨节点抢锁）+ NCCL 建组超时抬到 120 分钟（编译是合法工作，不该被当成 hang）。
失败 3 · 两个"看起来很对"的优化其实是致命的反直觉
  • expandable_segments:True：崩溃日志里写着「4.33 GiB reserved but unallocated」， 看起来正是碎片问题的教科书解法。但 torch_memory_saver/entrypoint.py:199 的 _sanity_checks() 会直接 raise——而 PPO 强制 offload_train=True， actor.py:76-78 必然会设 memory_margin_bytes 触发这个检查。 结果：job 在加载 checkpoint 之前就死了。所以只能留 max_split_size_mb:256， 碎片问题改用「降低每 stage 占用」来解。
  • 降低 EP：直觉上 EP 小一点每卡专家参数就少一点。但优化器分片因子同比例变化、精确抵消， 专家优化器字节/卡 = P_exp × 12 / 训练总卡数 完全与 EP 无关。 降 EP 只会让 per-rank 专家权重+梯度翻倍（6 B/param）而优化器项一分不减。⇒ EP 必须保持最大。
  • SGLANG_MEM_FRACTION_STATIC 用默认 0.75：会把约 71 GB 锁进 KV 静态池， FLA 长序列临时张量（l2norm_fwd_kernel、chunk_delta_h）随后撑爆剩余空间—— 这是在纯推理节点上实测到的崩溃。0.6 的代价只是 KV 池小、排队多（吞吐损失）， 用吞吐换不崩。

脚本里记录的一条重要历史结论（megatron_roles_...yaml 注释）： 在 27B + synth-2820 上试过 critic lr 10× 与 20×、oversampling 288 与 260 的组合， explained_variance 从 −39 拉到 +0.11 证明critic 学得很好很快， 但 rollout reward 五个 epoch 始终平坦。结论是「瓶颈 100% 在数据，不在 critic/lr/采样」。 这个 run 换掉数据（synth-2820 → tmax-15k 的 14601 个任务）就是为了打破那个奖励天花板—— 并且同时把 critic lr 推到 30×、actor lr 推到 2×。
