# GSPO + 长度reward + 课程学习 run 诊断报告

> **一句话结论:这次 run 不是训练代码出 bug,而是实验设置（课程难度排布 + RL 信号结构 + KL 约束）的问题。训练框架、GSPO、长度reward、entropy 监控全部按预期工作；模型本身也没坏（末期输出依然格式规范、推理连贯）。但实验的"数据顺序 + 奖励信号结构"组合,导致模型先过拟合简单套路、再被严格递增的难度拖垮,eval 单调下滑。**

- **Run**: `gspolen_20260616_130613`（Qwen3.5-27B, 96-GPU, TerminalWorld 1530 by_length 课程, GSPO, 长度reward λ=0.2, KL anchor 0.001, entropy off）
- **现象**: TB2 eval 越训越差 —— iter9 **41.6%** → iter49/79/99 全部 **22.5%**（精确卡死）
- **诊断数据来源**: 本地 `wandb/`（全量指标）+ `rollout_dumps/`（99 步真实轨迹），全部实测,非推测。
- **诊断日期**: 2026-06-17

---

## 1. 关键现象

| 指标 | iter9 | iter49 | iter79 | iter99 |
|---|---|---|---|---|
| TB2 eval (raw) | **41.6%** | 22.5% | 22.5% | 22.5% |

eval 从基座的 41.6% 掉到 22.5% 后**精确卡死**三次。第一反应会怀疑策略坍缩或代码 bug,但实测数据指向另一个更具体的因果。

## 2. 实测证据链（全部来自本 run 的 wandb + rollout dumps）

### 2.1 训练奖励本身就在下降（不止 eval）

`rollout/raw_reward`（训练任务实际成功率）按阶段统计：

| 阶段 | 平均 raw_reward | 区间 |
|---|---|---|
| step 1-10（课程最简单段） | **0.828** | 0.67–0.95 |
| step 11-35 | 0.747 | 0.52–0.91 |
| step 36-65（中/难段） | **0.575** | **0.24**–0.86 |
| step 66-99（最难段） | 0.636 | 0.43–0.82 |

step1=0.877 → step99=0.470。**训练任务上的成功率自己就崩了**,eval 只是忠实反映。这说明问题发生在训练过程内部,而非 eval 实现。

### 2.2 前期 72% 的 group「零梯度」——信号枯竭

GRPO/GSPO 的 advantage = group 内 reward 减组内均值。**一个 group 若全员满分（16/16 通过）或全员零分,组内 std=0 → advantage 恒为 0 → 该 group 不产生任何梯度。**

实测「零信号 group 占比」`(全对 + 全错) / 总 group`：

| 阶段 | 零信号 group 占比 |
|---|---|
| step 1-10 | **72%** |
| step 11-35 | 60% |
| step 36-65 | 41% |
| step 66-99 | 40% |

**前期每步 16 个 group 里平均有 ~12 个零梯度**,真正贡献学习信号的只有 3-5 个,且全是课程开头最简单的任务。模型实际上只在"极少数简单任务"上吃到梯度。

> 注：`rollout/rewards`≈1e-16、`rollout/advantages`≈1e-9 全程接近 0,这是 **group 归一化后均值为 0 的正常数学结果**,不是 bug；真正的问题是「有效（非零）信号 group 太少」。

### 2.3 模型没有坍缩——而是在「变发散」

- `train/entropy_loss`：step1 **0.178** → step50 0.244 → step99 **0.268**（持续**上升**）。健康 RL 通常 entropy 缓降（策略变锐）；这里在升,说明模型在变发散/不确定,而非坍缩到单一退化模式。
- `train/grad_norm`：0.35 → 0.38,无爆炸、无归零,优化器数值层面正常。
- `train/pg_clipfrac` 0.2–0.5、`ppo_kl` ~0.002：GSPO 裁剪工作正常,无数值异常。

### 2.4 真实轨迹解码：三个阶段对比（决定性）

直接从 token 解码出模型实际输出：

| 阶段 | 任务 | 输出形态 | 失败/成功原因 |
|---|---|---|---|
| **step 5**（易） | Hadoop pi 估算（一两行命令） | JSON 规范、6 turn、analysis/plan/commands 结构清晰 | **成功** |
| **step 64**（难） | 手写 ARM64 汇编 Fibonacci | **格式依然完美**、汇编有模有样,但 **2 turn 就 `task_complete:true` 草率收尾** | 任务客观难（汇编+syscall 细节错）,实力不足 + 过早宣布完成 |
| **step 99**（难） | pyOCD/CMSIS 嵌入式链；akash 区块链状态同步 | **依然规范**、5–27 turn、理性重试监控 | 任务依赖外部网络/部分根本无解,跑到超时 |

**关键**：末期（step99）成功轨迹依然规范、推理连贯、无重复刷屏、无乱码 → **彻底排除策略坍缩/退化为乱码**。失败的轨迹是"任务客观更难 + 模型实力不够",不是"模型坏了"。

## 3. 根因分析

### 3.1 因果链

```
by_length 课程（按 solve.sh 行数严格难度递增,无 shuffle）
        │
        ├─[前期] 课程开头是最简单任务 → 60-72% 的 group 全对/全错 → 零梯度
        │        有效信号只来自极少数简单任务
        │        → 模型过拟合「简单任务套路」：短输出、2 turn 自信收尾
        │
        ├─[KL anchor 仅 0.001] → 太弱,拦不住行为漂移
        │
        └─[后期] 课程推进到难任务（手写汇编、嵌入式链、区块链同步）
                 → 前期学到的草率套路（过早 task_complete）泛化失败
                 → 难任务大面积失败 → raw_reward & eval 双双下滑
```

### 3.2 为什么 iter9 是最高点
iter9（41.6%）≈ **基座模型的原始水平**。此时模型还没被前期的"简单任务套路"带偏。从 iter9 之后,每一步训练都在让模型偏离基座、过拟合简单套路 → eval 单调下降直到收敛到某个退化行为（22.5%）。

### 3.3 几个被排除的"嫌疑"
- **不是训练代码 bug**：GSPO/长度reward/entropy 监控/数据管线全部按预期工作,单测全绿,数值无异常。
- **不是 bf16/conversion 问题**：模型末期输出依然规范,无数值崩坏迹象。
- **不是策略坍缩**：entropy 在升不在降,输出无重复/乱码。
- **不是长度reward 失控**：实测 shaped bonus 全程 ±0.01,量级正确;且前期大量 group 全对/全错时,长度 tie-breaker 根本没机会介入。

## 4. 这是「设置问题」的具体含义

| 设置项 | 本 run 的值 | 问题 |
|---|---|---|
| **数据顺序** | by_length 严格难度递增,无 shuffle | 难任务全堆在后半段；前期简单任务大量零梯度。这是**最大杠杆**。 |
| **零信号 group** | 不过滤（全对/全错 group 照常进 batch） | 前期 72% 的算力浪费在零梯度 group 上,有效 batch 极小。 |
| **KL anchor** | 0.001（很弱） | 拦不住模型从基座行为漂移。 |
| **entropy 正则** | 关闭（coef=0） | 没有任何机制压制后期的发散趋势。 |
| **课程总长** | 100 step ≈ 1 epoch 单次扫过 | 难任务只在最后被看到几次,模型来不及在难任务上学会,就被它们拖垮。 |

**训练框架本身没有任何需要修的代码缺陷。** 需要改的是上面这张表里的实验配置。

---

## 5. 修复方向（按预期收益排序，供下次实验参考）

> 以下为方向性建议,具体实现可另起 plan。

1. **打散课程难度（最高优先）**：放弃严格难度递增,改 shuffle 或难度分层混采,让每个 batch 都有难有易 → 持续有梯度信号 + 不过拟合简单套路。
2. **过滤零信号 group / 动态采样**：用 slime 的 `--dynamic-sampling-filter-path`,训练前丢掉全对/全错的 group,只保留混合 group 的梯度（等效放大有效 batch）。
3. **加强 KL anchor**：0.001 → 0.005~0.01 量级,防行为漂移；或重新开启小幅 entropy 正则压制发散。
4. **难度配额**：控制每个 rollout batch 的 raw_reward 落在 ~0.2–0.8 的"可学习区",太易（全对）太难（全错）的都少采。
5. **（可选）课程多轮**：若坚持课程,应让数据多扫几个 epoch,而不是 100 step 单次扫过。

## 6. 附：诊断方法（可复现）

- **指标**：本 run 重启了 4 次,训练指标 history 在 `wandb/wandb/run-20260616_131600-*`（99 条）和 `run-20260616_131826-*`（297 条）两个 `.wandb` 日志里（最大的 3GB 日志只含 stdout + 系统遥测,无 history）。用 `wandb.sdk.internal.datastore` 离线扫 `history` 记录提取。
- **轨迹**：`rollout_dumps/<step>.pt` 是 `{'rollout_id', 'samples'}`,每个 sample 是 dict,含 `tokens`/`loss_mask`/`reward`/`status`/`group_index`/`metadata`。`response` 文本字段为空,但可用 tokenizer 从 `tokens[-response_length:]` 解码出真实输出。按 `group_index` 分组才能看到真实的 n=20 组内 reward 分布（`group_id` 在 dump 里退化为逐样本唯一,不能用来分组）。
- **关键判据**：`rollout/zero_std/count_0.0`（全错 group 数）+ `count_1.0`（全对 group 数）= 零梯度 group 数,是判断信号枯竭的命门。
